# DJC Next Plan

## Контекст

DJC - нативное iOS-приложение на Swift, SwiftUI и SwiftData для ведения танцевальных jam-групп по стилям Popping, Animation и Waving.

Приложение работает offline-first, без backend и iCloud. История переносится через CSV export/import.

Основная бизнес-логика генерации групп находится отдельно от UI и SwiftData в `JamOptimizer`.

## Уже реализовано

- SwiftData-модели `Dancer`, `Jam`, `JamGroup`.
- `DanceStyle`: `popping`, `animation`, `waving`.
- Стабильные `Dancer.id`, чтобы переименование не ломало историю.
- Поля танцора:
  - `displayName`
  - `nickname`
  - `firstName`
  - `lastName`
  - legacy `name`
  - `isArchived`
- Добавление, редактирование, soft-delete и восстановление танцоров.
- Archived dancers свернуты по умолчанию.
- Jam history свернута по умолчанию.
- Удаление ошибочно сохраненного jam из истории.
- CSV export/import истории.
- Import восстанавливает dancers по стабильному dancer id, обновляет поля и снимает архив при совпадении.
- README.md.

## Уже реализовано в JamOptimizer

- Optimizer отделен от UI и SwiftData.
- Принимает snapshot-структуры.
- Считает размеры групп минимум по 3 человека.
- Сохраняет всех present dancers ровно один раз.
- История фильтруется по выбранному `DanceStyle`.
- Минимизирует повторные пары.
- Учитывает частоту повторов относительно посещаемости.
- Недавние встречи штрафуются сильнее.
- Повторяющиеся целые группы штрафуются отдельно.
- Группы стараются быть максимально равномерными.
- Candidate generation усилен:
  - sorted rotations
  - reversed
  - sequential partition
  - round-robin partition
  - deterministic seeded shuffle candidates
- Есть конфигурация весов scoring и параметров seeded shuffle.

## Следующий этап

### 1. Объяснение результата генерации

Цель: пользователь должен понимать, почему optimizer выбрал именно эти группы.

Добавить в результат генерации:

- общий `score`;
- список пар, которые дали основной штраф;
- повторяющиеся целые группы;
- краткое объяснение выбранного варианта.

Архитектурно лучше держать это в optimizer layer, а UI только отображает уже подготовленный summary.

Возможное направление:

- расширить `JamOptimizerResult`;
- добавить структуру вроде `JamOptimizationExplanation`;
- добавить breakdown score по категориям:
  - pair repeats
  - attendance frequency
  - recency
  - whole group repeats
  - group balance
- покрыть unit-тестами без SwiftUI.

### 2. UX перед сохранением jam

Цель: перед сохранением показать предупреждение, если результат содержит сильные повторы.

Возможное поведение:

- если score или отдельный penalty выше порога, показать warning;
- показать конкретные проблемные пары или группы;
- дать сохранить все равно, потому что иногда выбора нет.

Важно: warning должен быть объяснением, а не блокировкой.

### 3. Настройки optimizer weights

После появления объяснения можно аккуратно улучшать настройки:

- сделать веса понятнее;
- возможно добавить debug/internal экран или простую конфигурацию;
- проверить реальные сценарии занятий на истории.

Пока не добавлять сторонние библиотеки и не делать backend/iCloud.

## Рабочие правила

- Отвечать по-русски.
- Двигаться пошагово.
- Не переписывать приложение целиком.
- Swift-код объяснять, потому что Swift новый для владельца проекта.
- Бизнес-логику держать отдельно от UI и SwiftData.
- Новые архитектурные решения сначала объяснять.
- Не добавлять сторонние библиотеки без необходимости.
- В итогах работы писать короткий план:
  - что готово;
  - что дальше.
